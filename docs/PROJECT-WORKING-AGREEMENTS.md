# AI-bot 项目协作准则

这份复盘覆盖 2026-09-04 建仓至 2026-11-26 主干 `2002f3f` 期间有记录可查的项目经历。它回答四个日常问题：这次做到哪里、谁来接、凭什么算完成、已有工作能否复用。各项约定直接用在现有任务、PR、交接或发布记录里。

## 开工与分工

1. **开工先约定交付终点。** 在任务开头用一句话写清“为谁解决什么问题，影响哪些端，做到哪一步可以交付”。审查、开发、合入、替换日常安装和正式发布都可以是终点。用户已经明确的范围直接执行，新增平台、改变已确认的交互或触及原授权以外的操作时，只确认新增部分。比如 Mac 专属签名修复可以单独交付，Windows 继续展示其实际公开版本。[Mac 单平台交接](development/MAC-FIXED-SIGNING-HANDOFF-20261126.md)

2. **接手先查现状，接着已有工作做。** 从当前主干、实际 PR 差异和原交接的最新回填查起，确认谁在做、哪份候选已验、剩什么。同一交付范围沿用现有分支和记录，独立交付或并行修改才隔离。后续证据推翻早期判断时，在原事项下更新结论和依据，避免下一位从一条过时的“待验”重新开始。[双端验收回填](development/WINDOWS-DEVICE-CENTER-HANDOFF-20261125.md) · [工作区保留规范](WORKSPACE-RETENTION.md)

3. **每次交棒，明确谁接哪一步。** 发起端写清场景、预期和已完成的工作；接收端核对本端，回填“已有等价行为、需要开发、只需复验或不适用”及依据。写到“待 Windows 验证”还不够，要让接手人知道从哪个入口操作、看到什么就算通过。桌面功能的代码与交接进同一个 PR；发起端满足合入条件后，接收端按既有流程跟进。正式发布由一人汇集原包并统一执行。[交接模板](development/CROSS-PLATFORM-HANDOFF-TEMPLATE.md) · [开发与发布分工](DESKTOP-DEVELOPMENT-RELEASE.md)

## 验收与决策

4. **先定通过标准，再报完成。** 标准写成用户能观察的结果，日常状态用“已合入”“已在 Mac 原包安装验证”“已在实体 TAB5 验收”“已公开发布”这样的具体动词。只填与本次交付有关的阶段，证据支持到哪一步就报到哪一步。未完成项写明接收方、缺的条件以及是否阻止本次交付。[手动切页首轮验收遗漏](STOCK_DISPLAY_FIX_2026-09-21.md) · [0.6.32 分平台验收记录](development/RELEASE-0632-ACCEPTANCE-20261125.md)

5. **让同一份证据可以交接和复用。** 结果跟随被验证的提交、原包和场景，换人、换电脑或换对话后仍可引用。候选文件有变化就登记新身份，按差异补验；纯文案修改沿用已验原包。能用模拟环境覆盖的异常路径先验证，只有真实账户、设备或用户授权才能回答的部分，才留到对应环境。交接时直接指出还差哪一次操作。[0.6.18 最小发布交接](development/MAC-0618-RELEASE-HANDOFF-20261105.md) · [升级确认的隔离验收](development/MAC-DESKTOP-UPGRADE-CONFIRMATION-HANDOFF-20261125.md)

6. **遇到未知或暂停，留下可恢复的交接点。** 分开写清观察到的现象、已经排除的原因、已经恢复的能力和仍待验证的判断。用户决定暂缓时，记录恢复工作的触发条件，先恢复现场，再结束本轮。会改变用户草稿、配对、权限、设备设置或产生实际外发的动作，遵守对应授权；结果未知时先查原回执。[升级中断暂停与现场恢复](OTA-WINDOW-CLOSE-INVESTIGATION.md) · [发送回执处理](development/TAB5-SEND-RECOVERY-DESIGN-20261031.md)

## 对外交付与收尾

7. **发布负责人按用户实际拿到的东西核对范围。** 从各组件上一实际公开版本核对本次变化，确认目标修复已进入候选，验收哪个文件就发布哪个文件。公开后从用户入口核对附件、双语说明、安装或更新路径。沿用仍准确的截图和视频，只改会误导用户的部分。涉及第三方素材时，按本次实际用途核对授权。[Mac 菜单修复的发布跟进](development/MAC-PERMISSION-RECOVERY-HANDOFF-20261122.md) · [发布收尾清单](RELEASE-CHECKLIST.md) · [素材授权实例](../licenses/companion-art/NOTICE.md)

8. **收尾时让下一位找得到结论，也拿得到原件。** 在原任务或交接末尾留下交付物、验证范围、剩余事项及接手方。先核对唯一补丁、待验原包和回退材料已有可用副本，再清理已合入分支、重复包和临时环境。内部记录保留追溯依据；用户说明只写能感知的变化、实际入口和必要操作。[工作区保留规范](WORKSPACE-RETENTION.md) · [发布说明模板](RELEASE-TEMPLATE.md)

## 哪些经历改变了我们的做法

| 项目经历 | 应保留的协作约束 |
| --- | --- |
| 小屏切页首轮检查了命令和请求模式，用户复测仍发现切页问题。第二轮把“提醒持续时，屏幕实际切到选定页”写入验收，才覆盖原反馈。[9 月验收记录](STOCK_DISPLAY_FIX_2026-09-21.md) | 需求里的用户动作要原样进入验收标准。这样开发和验收讨论的是同一个结果。 |
| TAB5 升级中断与关窗时间接近。隔离测试通过、现场短时未复现，用户决定暂停；团队保留日志、恢复原桥接，并明确原故障仍待定位。[10 月调查](OTA-WINDOW-CLOSE-INVESTIGATION.md) | “恢复使用”“定位根因”“验收修复”分别记录。暂停也要有明确的现场状态和续查条件。 |
| 0.6.18 的交接明确列出可复用的录音实测，以及最终 Mac 原包仍要补的安装和资料保留检查，Windows 统一负责后续发布。[11 月交接](development/MAC-0618-RELEASE-HANDOFF-20261105.md) | 接手人得到“直接引用哪些结果、只补哪几项”的答案，就能减少重复验证和来回确认。 |
| PR #44 的实际差异只有两份交接文档，Mac 实现及测试随后在 #45 合入。另一次，Mac 菜单修复已在源码中，0.6.31 公开包仍是旧行为。[PR #44 文件](https://github.com/yaoyouzhong/AI-bot/pull/44/files) · [PR #45 文件](https://github.com/yaoyouzhong/AI-bot/pull/45/files) · [菜单修复跟进](development/MAC-PERMISSION-RECOVERY-HANDOFF-20261122.md) | 报“已合入”查 PR 实际文件，报“已发布”查候选包含的提交和公开原包。仅凭标题、分支名或版本号容易报早。 |
| 0.6.32 的同一份跨端交接先记隔离回归，后来分别回填 Windows、Mac 封存原包接入实体 TAB5 的结果；公开验收记录引用同一交接。[交接回填](development/WINDOWS-DEVICE-CENTER-HANDOFF-20261125.md) · [发布验收](development/RELEASE-0632-ACCEPTANCE-20261125.md) | 原事项由接收方回填到底，发布负责人直接引用。后续对话打开同一处就能区分已完成与待办。 |

**以后怎样维护这些规则。** 再遇到返工，先查哪项既有约定没有执行、哪句话让两方理解不同。能修正原模板的一句话，就在那里修正。只有会再次影响项目决策、且现有规范确实没有覆盖的问题，才增加长期约束；一次性设备参数和排障步骤留在专题记录。
