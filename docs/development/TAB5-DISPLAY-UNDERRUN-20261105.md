# TAB5 间歇闪屏：LCD 欠载诊断与候选

用户在总览及其他页面反复看到屏幕左侧短暂闪动。保持已验收 `.315` 固件不变，通过 Windows 同用户后台 USB 诊断采样复现；不置顶电脑窗口、不触摸设备、不改显示设置。两次用户报告对应的采样窗口中，LCD 欠载计数在北京时间 14:47:30 从 6 增至 7，14:48:18 从 7 增至 8。两次 `flushErrors=0`、亮度 79、背光变化计数 14，UI 心跳仍新鲜。第三次报告发生在采样结束后，没有对应的计数证据。诊断结束已恢复原驻留桥接，配置文件和设备显示设置保持一致。

固定 ESP-IDF 5.4.2 的 DPI 驱动只在 `MIPI_DSI_LL_EVENT_UNDERRUN` 中调用本项目的计数钩子；驱动注释指出外部内存读取带宽不足，并提示考虑 AXI-ICM 仲裁。因此已确认存在 LCD FIFO 欠载。具体带宽争用来源尚未独立测定，不能把推断称为已证实根因。

项目已有 `display_bandwidth.c` 仅在照片冻结到解除期间把 DW-GDMA 内存读取主端口的仲裁和读 QoS 设为 15，解除后恢复此前值。普通总览、对话和屏保没有同样的基线保护。原诊断 `bw,1,0,0,0,0,0` 的末两位是旧代码的缓存字段，不能当作实际寄存器测量值。

候选将相同的既有保护扩展到显示生命周期：在 `ui_start()` 前初始化，照片解除后继续保留。只改 DW-GDMA memory master 1 对应的 `gdma_mst2` 读取优先级，其他主端口和全部写 QoS 保持不变；诊断改为读取实际寄存器。固定 SDK 的 `axi_icm_ll_set_dw_gdma_qos_arbiter_prio()` 确认该主端口映射，固件静态断言检查实际 SDK 的 memory enum 仍为 1。没有更改 SDK、PSRAM 频率、屏幕时序、配置或桥接协议。

这是针对已确认欠载和既有保护范围缺口的候选修复，尚不能宣称消除闪屏。持续提高读优先级可能影响并发数据传输，必须补充拍照和语音场景真机检查。

主机回归编译实际生产 `display_bandwidth.c`，使用固定 SDK 的真实 ICM 寄存器结构，仅替换 RTOS 锁和主端口 enum 的主机依赖。旧生产代码在“照片解除后仍保留保护”的同一断言上失败，新代码通过；覆盖启动无照片、重复初始化、重复 begin/end、后续照片、其他寄存器位和写 QoS 不变、诊断真实读回及临界区平衡。该回归证明策略代码行为，不模拟硬件吞吐量。固件构建仍编译真实 SDK enum。
