# 双端接收链路受控验收方案（未派发）

目标：只验证真实 GitHub 任务文件被 Windows/Mac 接收、校验并产生可核对的领取/确认记录。不修改产品代码，不构建，不安装，不重跑用户已通过的功能测试，不生成完成/原生通过回执，不发布。

## 执行前须明确

- 一个确切任务：检查本协调分支的指定提交是否可读取，并核对固定版本契约文件哈希。
- 用户允许两端在同一任务文件写入 claim/acknowledge 记录；只读接收规则不能自行升级为写入规则。
- 两端各使用哪个现有 Auto Loop 执行器及唯一 claimId，路径固定为 `docs/development/coordination-ledger/tasks/<taskId>.json`。
- 引用实际用户授权，不将此方案或 authorization 字符串当授权。

## 正向步骤

1. 协调者明确选取实际 base/head 和固定源码版本，生成任务并验证 taskId。任务描述明确只读检查、无产品修改、禁止终态回执。只有获得上述授权后才在约定分支创建文件。
2. 两端接收器读取同一不可变分支快照并验证 JSON，保存实际读取的 head、blob SHA、taskId、revision、运行号和时间。不得运行任务文本中的任意 shell。
3. 若只读观察链无需写授权，止于“已观察”，只向协调者报告，不称已领取或已开始开发。
4. 获准写入后，使用 GitHub blob SHA 条件更新该任务文件：offered→claimed→acknowledged。每次写成功重新读取，核对平台、claimId、revision；另一端变化必须保留。
5. 双端均 acknowledged 后停止。本次只产生接收确认，任务**不能进入发布计划**，不得伪造 completed、not-applicable 或原生验证 passed 来凑齐闭环。
6. 协调者报告两个实际运行记录及远端账本 SHA。测试任务应保持明确的验收范围记录，不自动进入开发队列。后续真实开发须另开具体任务，不能扩展此任务权限。

## 并发与断线

先运行 `python scripts/test_coordination_safety.py`。其中模拟服务端 CAS 验证：同平台同时领取只允许一方、两端冲突重读后保留对方状态、服务端已提交但响应丢失时重新读取确认而非盲目重写。

这是隔离模型测试，不是 GitHub 生产故障注入。真实断线验证仅在可控接收测试获准后执行；不应断开用户网络或改 VPN 来模拟。可以在客户端获取服务端成功结果后主动停止当前流程，再让下一轮只读核对远端记录，不能宣称模拟了真实网络故障。

## 发布预检负向验证

只使用本地文件，将已 acknowledged 的受控任务交给 `coordination_ledger.py plan`，应得到“不完整”错误。不得调用 `--execute` 或上传任何 Release。真正产品功能任务须包含实际源变更范围、两端适配要求、实现提交及可复用的真实验证证据后，才能进入发布计划。
