# ESP8266 股票绘制栈破坏调查与修复

## 已确认的故障与来源

2026-11-02 Windows 真机采样在轮播天气页之后出现设备信息超时，随后 `uptime_ms` 从约 58 秒回到约 4 秒，股票绘制计数保持 0。桥接补充只包含计数及固定错误标记的后台诊断后，直接捕获 `Stack smashing detected.`、`Exception (5)`、`ctx: cont`；刷机前累计 9 次栈破坏标记。没有保存串口数据正文或栈内存内容。8 项启动资源均曾 ACK，不能由此推断持续通信正常。

Git 历史显示，`29474d7`（2026-11-02）在股票等宽字形实现中新增 `uint16_t codePixels[56 * 16]`，占 1792 字节。此前 `889d6a7` 直接调用 `display.drawString`，没有该局部数组。因此这一大幅栈占用增加来自最近的股票字形改动。当前固件的股票绘制与异常、重启时间相关；不能将 Windows 原生字形回归或 Mac 先前视觉接受视为覆盖了栈安全与长时间运行。

ESP8266 Arduino 3.1.2 的默认 continuation 栈为 4096 字节。Windows 修复前实际 Xtensa 产物中 `drawStocks` 入口分配 32 + 0x7a0 = 1984 字节，且在该栈帧内调用股票名称的 LittleFS 文件读取，再进入文件系统和显示调用链。Windows 串口同时仍保持打开，既有桥接忽略周期心跳未回复，继续尝试资源；“已连接”或“最近主机写入”不能证明设备未重启或仍有有效回包。

## 最小修复与验证方法

在 `firmware/src/main.cpp` 将原样的位图生成和 `pushImage` 放入独立的 `drawStockCode`，显式禁止内联；文件读取结束后才调用它。数组不再与 LittleFS 调用链共用 `drawStocks` 的大栈帧。没有把数组转入长期堆或全局 RAM，没有改变字模、像素、位置、代码截断、用户亮度、过渡、协议或轮播配置。

修复后实际 Xtensa 产物保留独立 `drawStockCode`，栈帧 32 + 0x730 = 1872 字节；股票调用方被内联到 `loop`，其入口栈帧为 0x140 = 320 字节。文件读取路径不再承受原来 1792 字节像素数组的额外占用。全局 RAM 仍为 46200 字节。PlatformIO 构建通过，既有股票生产字模、过渡、资源去重原生测试和背光检查通过。构建存在原先的触控宏、未使用变量和日期格式等警告，未修改无关代码。

候选应用：`artifacts/esp8266-stock-transition-20261102/stack-fix-candidate.bin`，SHA-256 `d82c7adb624b2e87f9f79c0323a13908f49bd03d2a9be1354bad4b8b507ef079`。候选 ELF 同目录保留；此为 Windows 本地未提交工作区构建，不是正式版本或 Release。

## Windows 自动启动路径

直接由 Codex 启动会继承 MSIX 文件目录重定向，原有 `AppProfileGuard` 按预期拒绝；不放宽保护，不从重定向配置推断当前设备身份。此前没有完整检查后台入口就要求用户手工启动，现已修正排查路径。

Windows 已有指向固定入口的 `AI-bot-Logon-<当前用户 SID>` 登录任务。核对任务只有一个动作、路径与候选固定入口一致、参数为空、Interactive 登录、Limited 权限、启用状态后，先以仍运行的桥接验证重复启动正常退出（结果 0），再发送 `--exit` 并等待主进程和守护正常退出，最后启动该既有任务。已成功自动启动并从新增诊断字段确认新程序运行。没有创建或改写任务，没有提升权限或抢占前台；后续可沿此现有机制后台重启。
