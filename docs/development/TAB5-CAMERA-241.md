# TAB5 相机连续内存修复 .241

## 实测依据

.240 已刷入并核验指定 ELF、`ota_1 VALID`。用户曾成功添加两张照片，但“拍一张→添加附件→关闭→再次打开”仍失败。保持错误现场、不重启设备，正常退出 Windows 桥接后，从 COM9 读取到：

```text
esp_video_buffer: frame=3/3 size=1843200 align=64 caps=80404 free=7972652 largest=1277952
```

这是分配第三块 CSI 帧时的数值，采样在失败池回收之前。总空闲 7,972,652 字节，但最大连续块只有 1,277,952 字节，无法放入 1,843,200 字节的全尺寸帧；确认该次 `6/12` 来自碎片化。这里不能推广为所有相机内存故障，也不能把历史 .064/.087 的通过记录解释成从未修过。

## 修改与所有权

旧路径同时保留三块 MMAP 采集帧和另一块全尺寸静帧。新路径使用已固定的 esp_video 0.7.0 所支持的 `V4L2_MEMORY_USERPTR`，把静帧作为下一次预览的三帧之一。总共同时占用的全尺寸帧由四块降为三块：7,372,800 → 5,529,600 字节，减少 1,843,200 字节。分辨率、RGB565、三个预览所有者、JPEG 质量 85 均不变。

- 从 LVGL 入口先隐藏旧静帧，再允许 DMA 复用；第一张新帧仍在 LVGL mutex 内绑定。
- 完成拍摄或关闭时先成功停止采集，直接把当前显示帧移交静帧所有者，不复制整帧。结束显示交接，显式 `REQBUFS(0)` 释放驱动元数据，再释放另外两块帧。
- JPEG 仍使用不可变帧租约，编码完成前禁止重开或重拍。已有附件、缩略图和草稿不回收、不重写。
- 停止采集或释放元数据失败时，明确保留三帧并禁止重开，等待设备重启；不能在驱动可能仍访问时释放内存。保留首个驱动错误记录。
- 已检查协议对端的 USERPTR 请求、查询、入队、出队、对齐和外部 RAM 校验，以及析构不释放外部所有权的行为。ISP 自身的 MMAP 请求仅针对独立的统计元数据流，不修改它。

本次没有修改 Windows 或 Mac 源码、电脑绑定及通道选择。读取现场后从正常资源管理器恢复固定 Windows 运行程序；资料目录、配对文件时间及 DLL 哈希未变。随后 Windows 未枚举到 TAB5 USB 端口，暂不把桥接启动当成 USB 连接验证。

用户随后重新接入 USB，已确认 COM9、所选 Windows 电脑经 USB 认证、新鲜心跳和仍为 .240 的相机错误现场。对应数字字段保存在 `hardware-before-241.json`，未重启设备或要求重复拍照。

## 本地验证

实际相机工作线程在原生夹具中同时最多允许三块全尺寸帧。对保留的 .240 实现，同一测试复现第四次分配失败，阶段 6 / ENOMEM 12；恢复新实现后，两种显示路径各 64 次拍摄/重开通过，总计 128 次。每次结束只保留一帧、峰值三帧，租约期间不允许重开，附件读取的全部像素仍为最后拍摄帧。还覆盖部分分配、入队、启动、显示恢复、停止及元数据释放故障。夹具的硬件接口为模拟，不能代替传感器/DMA 真机验收。

八项相机相关原生目标已通过。固件构建、实际说明预览、补丁重放与精确镜像信息完成后登记在 `artifacts/development/tab5-camera-20261022/FIRMWARE-241.json`。新候选真机验收尚未完成；不会以本地 128 次循环代替用户实际拍照、加入附件、退出后重开的结果。

最终构建、完整 LVGL 回归、实际 sidecar 顶部/滚动图片检查及三文件补丁重放已通过。补丁按 Git 的 LF 规范化文本验证；原始源码字节哈希单独记录。镜像 7,156,672 字节，SHA-256 `0248e30a33b743286becb59b83b971e74d4b6045d5d7a3a2b0bcade8790798f1`；ELF `77ce04d1fc02c0a37386cde634fa4c82835af1c0d3d40e52ae43a85e0ef8aad1`。标准入口及历史归档均已核验，`PREPARED-241.json` 保存构建阶段证据哈希。
