# 0.2.44 蓝牙翻页与网络曲线候选

## 翻页等待

0.2.43 的提示修正没有解决耗时：完整状态超过 6 秒时，UI 不发起读取；RPC 通道选择也要求完整状态在 8 秒内。蓝牙即使刚完成历史页回复，也可能等待下一份较大的完整状态，再等待原来的重试周期。

0.2.44 的 `read` 操作允许使用同一连接、同一桥接 session 最近 8 秒内通过认证的成功 RPC 回复，前提是原完整状态不超过 90 秒且邮箱仍有最近活动。断开会清除证明，连接代次变化后迟到的结果不能恢复它。Wi-Fi、发送、附件上传、草稿等操作和日常通道优先级保持原检查；HMAC、AES-GCM、nonce、防重放和桥接 session/time 检查不变。正在等待的翻页每 250 ms 检查是否可重新发起，不再额外等 6 秒。

新固件只在 USB/BLE read 请求声明 `rpcReplyVersion:1`。新桥接在外层 RPC 已认证加密的响应中直接返回历史正文，去掉内层重复加密/base64。HTTP 即使声明此字段仍返回原加密封装；旧 RPC、旧桥接保持兼容。保留邻页缓存。模拟同一历史页响应 805 → 517 字节（约减少 36%），不是实际延迟降幅。

## 网络曲线

原小包仅带最近 12 个 250 ms 样本（约 3 秒），完整状态实际也由这份截断 Samples 产生。BLE 传输/RPC 等待超过该窗口时，设备拿不到遗漏样本，0.2.43 的留空逻辑造成曲线反复断开。

桥接现从已有 History 中带最近 64 个原始样本（约 16 秒），完整状态和指标小包一致。支持安全解压的接收端将较大的指标包 zlib 压缩，模拟 64 点数据 2667 → 1244 字节；不支持者保留原明文内层格式和外层加密。固件按序号补齐实际样本，每秒绘制一个 2 秒移动平均点，显示约 2 分钟；没有补造丢失样本，超过保留窗口的真实断档仍留空。CPU、内存与网络数字指标不因曲线平滑而额外延迟。
