# 0.2.64：会话相机入口释放绘图缓存

## 真机证据与影响

0.2.63 图片添加成功，但用户仍认为太慢：122120 字节、BLE、77974 ms、200，实际 `flow=notify4/write4`，MTU 517。约 1.53 KiB/s，相比 0.2.62 的 97559 字节/104244 ms 有效速率提高约 67%；两张内容不同，不能作为严格同文件基准，更不能据此验收速度通过。证据在相邻 AI-bot `artifacts/acceptance-20260930/photo-063-upload-success.txt`。

请求用户再拍照以抓取完整分段时间时，遇到“相机缓存区不足，请重新打开 (6/12)”。现场 `cameraDiag=6,12,...`，发生于 VIDIOC_REQBUFS，在相机取帧前；照片/上传诊断仍为上次结果，不能算本次上传成功。`displayDiag` 的 `tab5_cache_bytes=5036544`、`tab5_native_cache_bytes=5036544`，两类绘图缓存合计 10,073,088 字节（约 9.61 MiB）。诊断保存在 `camera-063-reopen-memory-failure.txt`。

源码核对：应用相机入口先调用 `tab5_draw_cache_drop()`，Codex 的 `photo_open()` 却直接启动相机，重拍分支也没有释放缓存。CSI 要申请三块 1280×720 RGB565 缓冲区（共 5,529,600 字节），使用 PSRAM/cache-aligned 分配。后台可重建缓存仍占用大量相同内存，入口不一致是此次明确修复点；实际释放后的真机成功仍需验收。

## 最小修正

- Codex 相机入口和重拍分支在启动相机前释放绘图主缓存、旋转副本和暂存区，沿用应用相机已有机制。
- 不删除已添加照片、缩略图、草稿或照片预览，不改相机三缓冲所有权、分辨率、质量、配对及连接方式。后台缓存可在退出相机后按原机制重建。
- 保留 0.2.62 编码内存修复及 0.2.63 蓝牙窗口协议。本次不替换桥接，也不把相机缓存修复说成蓝牙速度已修复。

## 验证与后续

真实 LVGL 预览测试先分配有效页面缓存，再通过排队的会话拍照入口打开相机，确认相机启动时两类缓存均为零。退出后重新构建缓存，连续重复三次，确认每次都释放且两张已有附件的 ID 保留；原排队一次、离页取消、发送互斥、相机遮挡检查同时通过。固件构建和镜像/ELF 检查结果记录在冻结候选验证文件。

5 分钟只读耗时采样已结束，173 条变化记录中没有新的图片上传状态，因为相机启动被阻挡；不能从该采样推导本次照片分段占比。原速度记录可见后台完整状态传输和 RPC 排队达秒级，但不能把事后历史读取时间当成照片分段耗时。修复并确认相机可连续打开后，继续在仅蓝牙下抓取完整上传，分清请求、处理、回复及排队，再调整传输调度。升级前保持原错误现场，无需重复配对。
