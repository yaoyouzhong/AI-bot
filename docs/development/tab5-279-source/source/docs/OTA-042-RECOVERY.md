# 0.2.40 回滚与 0.2.42 修复验收

## 实机结果

- 首次固定蓝牙 0.2.39 → 0.2.40：桥接提供 16 KiB 后失败。
- 首次自动模式 USB：桥接提供 3809280 / 6594960 字节后停止，用户确认下载失败。缺少 USB 首次异常日志，根因未确定。
- 增加诊断后 USB 复测：16:00:47 至 16:03:18 观测到全量传输，约 151 秒、43 KiB/s。传输中没有 USB RPC 异常；16:03:23 的异常处于完成后的重启阶段。
- 曾收到 0.2.40 hello，但后续只读启动验收发现回滚至 ota_0 / 0.2.39 / VALID。回滚记录 crash=1，previousBootStage=3，previousHealthySeconds=8；不能将此次升级标记成功。
- 证据：`.tools/usb-ota-diagnostic-041.jsonl`、`.tools/usb-ota-040-verified/installed-040.json`。后者 `verified=false`，必须保留失败结论。

## 明确缺陷和修复

返回地址 0x4001c886 对应冻结 0.2.40 ELF 的 `receive_frame` 压缩解码调用。ESP32-P4 ROM 的 `tinfl_decompress_mem_to_mem` 便利函数汇编分配约 0x2B00 字节工作栈，而 Wi-Fi 任务栈为 8192 字节、NimBLE 为 4096 字节，存在明确的栈容量错误。

0.2.42 改用底层 `tinfl_decompress`，将每次解压工作区分配在 PSRAM，使用非环形输出标志，检查完整输入消耗、精确输出长度和完成状态，失败时释放全部工作区。没有增大线程栈，也没有关闭回滚或健康检查。

配套桥接仅向 0.2.42+ 的已验证 Wi-Fi 接收端、或声明 `telemetryVersion:2` 的 BLE 接收端发送压缩状态。0.2.40/0.2.41 保留小包更新但使用未压缩完整状态，以避免触发旧解压路径。

0.2.42 同时包含 0.2.41 的 Wi-Fi 优先、USB 备用升级策略、首批数据 KB 进度和升级页优化；蓝牙固件下载按用户明确要求停止。日常数据连接优先级保持 USB > Wi-Fi > BLE。

## 完成边界

0.2.40 与 0.2.41 候选均撤回，不再提供升级。0.2.42 已通过下面记录的 Wi-Fi 升级和启动健康验收。USB 约 58% 的偶发中断尚未复现到首个错误，不能因一次全量传输成功而宣称已修复。蓝牙会话读取、纯蓝牙电脑状态刷新体验和主页面滑动流畅度仍需独立验收。
