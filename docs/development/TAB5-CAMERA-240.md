# TAB5 拍照缓存回归修复候选 .240

## 问题与历史证据

同一设备在 .238 再次报告 `6/12`，帧数为 0，首个驱动错误为 `esp_video: Failed to create buffer`。现有证据定位到帧池分配，但清理后的总空闲 PSRAM 不能确定失败瞬间的连续内存。

此前确实修过同类问题：.064 补齐 Codex 相机入口及重拍的绘图缓存释放；.087 解决 ISP 多引用下帧池未及时释放。`AI-bot/docs/CAMERA-RECOVERY-087.md` 和 `ACCEPTANCE-2026-10-02.md` 明确记录过三轮拍摄/重拍/退出、三轮添加/移除/重开及附件实际送达通过。核对当前源码，这两项修复均仍存在；本次没有将历史通过记录抹去，也不把旧修复重复当成新修复。

当前另有可从生产代码确认的资源交接缺口：退出图库只隐藏界面，UI 的完整解码图仍由 `gallery_cache` 持有；前台解码完成后还可能把图交给 `result`，只在图库可见时由 `gallery_update()` 接收。原 .235 的交接等待会清压缩缓存、空闲 HTTP 和 spare，却未覆盖这两个所有者。图库两块全尺寸 RGB565 图片每块 1,843,200 字节，会与相机三帧申请争用相同 PSRAM。这里确认的是漏回收路径，仍不把它宣称为已实测证实的全部 ENOMEM 来源。

## 最小修复

- 三个相机入口共用 `camera_release_caches()`：在 LVGL 线程先解绑图库图片源、清除已显示指针，再回收隐藏解码图；继续沿用绘图缓存释放。照片草稿和附件不参与回收。
- 相机工作线程在图库工作结束后接管并释放尚未交给 UI 的 `result`，再清理 spare。不强制释放仍在工作线程中使用的图片，不在共享 mutex 中执行 HTTP 清理。
- 只保留原作品/页码的元数据，返回图库时重新开始正常重试窗口并加载该页，避免拍照时间较长后等待旧计时或退回第一页。
- 保留 .238 通道归属、1280×720、三帧所有权、JPEG 质量、绑定/配对/网络和显示设置；Windows 与 Mac 源码未改。将 .239 的失败前诊断一并带入修复候选，.239 从未刷入。

另外三项图库工作线程、DMA 缓存同步和 JPEG 缓存回归通过，共十一项原生目标。完整 LVGL 回归通过；真实 LVGL 三轮夹具在相机启动观察点确认两块解码图已解绑、描述符及缓存归零，草稿中的两张原附件仍在。返回图库的检查确认旧重试窗口过期后会重新建立窗口，并请求、显示同一作品页码。实际 sidecar 的顶部和滚动截图均已检查；模拟当前版本仍是预览夹具，不用于证明设备版本。
