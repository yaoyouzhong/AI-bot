# 跨平台交接模板

Windows 或 Mac 功能改动的 PR 应在同一个 PR 中新增或更新 `docs/development/` 下的 `*-HANDOFF-*.md`，例如 `WINDOWS-UPDATE-HANDOFF-YYYYMMDD.md`。发起端提交前填写交接判断、共同要求、对齐初判和验收步骤。发起端完成适用测试、CI 和审核后可合入，接收端在合入后按[统一开发发布流程](../DESKTOP-DEVELOPMENT-RELEASE.md#开发与交接)核对本端结果并跟进 QQ 审批。

- 是否需要交接：<需要 / 不需要>。<接收端下一步，或无需交接的依据>。
- 接收平台：<Windows / macOS / 不适用>
- 发起端对齐初判：<需要 / 不需要 / 待接收端核实>。<源码、实测依据或具体待核实的问题>。已有等价行为但仍需复验时，填写「需要交接」「不需要对齐」。多项结论不同时，逐项填写下方清单。

## 对齐清单

有跨端影响时，每个可独立验收的场景复制一份下列条目。两端预期相同时合写一行；允许表现不同的，分端写明差异及依据。接收端已有相同行为时，记录核对依据和状态。

### <事项 ID / 优先级 / 场景名称>

- 适用范围：<两端共同要求 / 平台专属 / 另一端可选>。依据：<协议条款、既有用例或本次确定的产品要求>。
- 场景：<用户或设备处于什么初始状态，执行什么操作或遇到什么事件>。
- 预期表现：<Windows 和 macOS 在该场景下各自应显示、发送或保留什么>。
- 验收步骤和通过标准：<每项写明负责平台、前置条件、操作及预期结果。有现成用例时给出命令或链接，注明哪些必须真机验收>。
- 发起端初判与结果：<发起端实现位置、已完成的检查和证据，以及对接收端缺口的初步判断>。
- 接收端核对结果：<合入后由接收端填写：缺少实现 / 已有等价行为 / 仅需复验 / 待确认范围>。<本端实现位置、已有证据和下一步>。
- 对齐状态：<待对齐 / 已对齐 / 已有无需修改 / 不适用 / 待验证>。<剩余问题、接收端下一步及是否阻止发布>。

有具体待办时，另起一行写明端和场景，例如 `待对齐：Windows｜打开更新面板时刷新状态`。接收端得出结论后，在原事项下写本端结果及验证依据。有对齐 PR 时一起更新原文档。

填写示例：天气页已显示上次成功获取的气温，下一次刷新超时。两端都应继续显示原气温。验收时先让天气服务返回 18 °C，再模拟一次超时并刷新，检查两端页面仍显示 18 °C。实际执行后，再分别填写结果和证据。
