# TAB5 R5 总览闪屏与 R6 本地候选

11 月 12 日通过常驻 Mac 桥接的 USB 诊断读取同一台未重启的 TAB5。实机仍运行 `0.2.320-ui` R5；参见 [R5 实机记录](MAC-TAB5-R5-PHYSICAL-20261112.md)。没有切换显示模式、接管串口或写入设备。

- 早前报告左侧闪屏后读到欠载计数 2。随后被动采样约 178 秒（90 样本），总览、无屏保、79% 亮度、背光变化计数 3、绘制错误 0；搬运计数增加 2511，欠载仍为 2。
- 14:46:11 读到欠载计数 3，随后用户报告又闪一次，14:46:36 读到计数 4。两份快照均为总览、无屏保，背光和绘制错误计数不变，诊断均显示正搬运 40352 个 RGB565 像素（80704 字节）。读到状态时的搬运年龄分别为 4229 μs 和 4451 μs，两次都在 LVGL 提交刷新后的阶段被读到；第 4 次还与页面快照缓存构建重叠，第 3 次没有。把欠载记录的 32 位设备计时与该次回执的开机时间对齐，估算两次锁存读取约在 14:45:08 和 14:46:15（北京时间；回执时间取整，未与肉眼观察同步）。
- R5 在显示 DMA 完成回调读取并清除欠载锁存位。上述年龄是读取锁存位时的搬运年龄；锁存位可能在这次搬运之前已置位。计数是回调看到锁存位的次数，不能作为硬件欠载次数或具体闪屏帧数。重复关联加强了扫描与帧缓冲搬运争用的判断，还不足以确定谁先发生。

在当前显示路径中，DMA2D 从 PSRAM 绘制缓冲搬到 PSRAM 帧缓冲，同时 DW-GDMA 从 PSRAM 读出显示数据。更直接的问题见 [锁定版本的 ESP-IDF DPI 驱动](https://github.com/espressif/esp-idf/blob/f5c3654a1c2d2a01f7f67def7a0dc48e691f63c0/components/esp_lcd/dsi/esp_lcd_panel_dpi.c)：发现欠载后先用 `ESP_DRAM_LOGE` 输出，再恢复 DMA 链表和使能扫描通道。本构建控制台使用 UART0 115200；同步日志位于扫描恢复的关键路径，可能拉长已有异常。尚未实测它拉长了多少，也不能用它解释第一个欠载。

[R6 源码补丁](TAB5-320-R6-SCANOUT-REARM-20261112.patch) 移除该回调中的串口输出，保留计数、状态清除、重新使能扫描和刷新回调。面板时序、FIFO、水位和 32 字节突发配置保持不变。诊断只在帧缓冲搬运边界读硬件锁存位，不清除；沿用诊断字符串并附加可选 `copywindow,1,stable,read_frame,begin_frame,begin_flag,end_frame,end_flag`。读数 0/1/2 表示清除/置位/未知；未完成、跨帧或不稳定时不得据此推断先后。清除边界存在并发，采样窗口不是欠载中断的时间戳。USB 只有在完整旧回执与绑定、OTA 和自动化信息组装后仍有空间时才添加这段数据；旧 Mac / Windows 桥接继续处理原字段，无需同时更新。

本地验证：

- 补丁在九个 R5 文件（六个生产文件、三个测试文件）的独立干净前像通过 `git apply --check`，应用后与候选逐字节一致；SDK 补丁可重复应用。私有工程通过归档的 .318/.319 和 R1–R5 生产增量构成，未宣称可逐字节重建原 R5 镜像。
- `scripts/test_tab5_scanout_rearm.py` 使用 SDK 的实际 C 回调和诊断实现：验证 R5 输出先于重启 DMA、R6 不输出且保留诊断和恢复，以及锁存采样、回绕与并发样本拒绝。还验证新增后缀在空间不足时不改动 USB 旧回执。无线运行诊断及 USB OTA 回执原有测试已更新并通过，包括旧输出、加上后缀和超出容量后保留旧输出。
- 锁定工具链和 ESP32-P4 配置原生编译了 `esp_async_fbcpy.c`、`esp_lcd_panel_dpi.c`、`display_diagnostics.c`、`runtime_diagnostics.c` 和 `usb_link.c`。反汇编核对三个诊断钩子位于 IRAM；新回调仍引用重启扫描和欠载诊断，不再调用串口日志。随后在同一私有工程以原生构建脚本完成全量 ESP32-P4 编译、链接和镜像生成。最终 ELF 中三个钩子和扫描回调均位于 IRAM，扫描重新使能和欠载诊断仍在，回调没有串口输出调用。

本地 OTA 候选 `0.2.320-ui` / `320-R6` 已由 `prepare_tab5_firmware.ps1` 校验和归档到固定 `artifacts/firmware/tab5/latest/aibot_tab5.bin`。镜像为 7,056,800 字节，OTA 应用分区余量 152,160 字节。BIN SHA-256：`fe0908fc05d1a62d8124237892d391c196e6bd0ac1eccd4776e1f496c572897d`；嵌入 ELF 指纹：`50e88b8d89f646453f448ddf6da69fbc93e5be2210885d4006687a729ba96e89`，与实际 ELF 相同。实际配套更新说明使用相同 LVGL 渲染代码、布局和字体离屏预览，分类和条目均完整可读。上一份固定路径的本机候选仍在历史归档；当前实机 R5 的原包见 Windows 交接中的归档记录。

待验证：在可刷的台架或获准的部署窗口，以相同总览、亮度、供电和连接方式比较 R5 与候选。采集至少覆盖本次复现时长，同时记录真实面板和欠载计数。若计数仍增加，核对稳定搬运窗口内锁存位先后，再决定是否调整 DMA 搬运切块或带宽；即使肉眼不再闪，也须区分“缩短了恢复”和“消除了欠载”。以上为部署前的验证计划。

## 长测结果：新增欠载

按用户确认的验收标准，LCD 欠载／绘制错误任一计数新增就不判屏闪通过。此次 1329 份样本中，999 份符合总览、79% 亮度、无屏保；排除切换测试造成的采样间隙后约 1246 秒。17:30:37（北京时间）总览 LCD 欠载 0→1、绘制错误仍为 0；上一回亮度变化在约 3 分 25 秒前。自动采样因首次新增欠载结束。这是诊断验收失败，不代表有人看到当时的屏幕。

本次捕获 `copyfault,1,1,1808,4500,18720` 和 `copywindow,1,1,125266,125265,1,0,2`。稳定窗口里第 125265 帧读到置位的硬件锁存，读取点在 DMA2D 两个通道启动前；第 125266 帧的回调记录了该欠载。正在进行的是 18720 像素的搬运；它开始前就已出现欠载，不能把这笔搬运认作触发点。上一笔搬运约在本笔开始前 2.7 ms 完成（按两个年龄的差值）；现有记录不覆盖更早的触发时刻。后续同一开机回读中，未记录超过 50 ms 的帧回调间隔、Flash 保护或看门狗，不能据此排除更短的调度或访存压力。下一步优先关联前一笔搬运、LVGL 渲染／CPU 旋转与欠载的先后；没有再次刷机或改显示设置。
