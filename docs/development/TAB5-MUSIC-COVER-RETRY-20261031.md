# TAB5 音乐封面重试调查（2026-10-31）

## 现场与边界

设备 .296，Mac 本地 R45。用户报告上一首封面停在 100%，下一首百分比反复循环。用户随后明确更正：底部导航一直可以离开音乐页。因此不能将此记录为触控冻结或死锁。

为停止资源重发，临时停止已核验的桥接进程；“连接电脑后可控制播放”由此产生，并非新增连接故障。未改音乐偏好、未控制播放器、未刷固件、未置顶电脑窗口。

## 已确认的代码问题

`MacTab5Assets.projection` 在设备尚未报告目标 CRC 时无限把偏移归零。状态、USB、BLE、Wi-Fi 共用同一份资源游标。整图没有确认时，没有重试次数和等待窗口。

设备 `assets_receive` 在持有 `device_mutex` 时校验 CRC 并解码，失败后释放接收缓冲；下一轮会重新接收和解码。`assets_progress` 在旧图片仍存在而新接收缓冲已释放时返回 100%，不能据此认定新封面已解码或已显示。

具体曲目的失败原因尚未证实：需区分资源持续变化、完整接收后解码失败、设备已确认但显示未更新。不能将重试上限等同于封面显示已修复。

## 桥接保护与诊断

同一份封面最多完整下发三轮，每轮后等待两秒。状态刷新和传输通道切换不重置预算；资源身份变化才开始新预算。停止无效封面重发后，状态、控制及其他资源照常处理。晚到的确认仍有效。无协议字段变更、无固件部署。

后台只保存固定数值：宽高、字节数、偏移、轮数、JPEG 标记、设备确认状态、次数、资源代数及进程/时间。不保存封面、曲名、请求或会话内容、凭据。离线验证使用合成像素和注入时钟，覆盖丢失确认、迟到确认、重复状态刷新、三轮耗尽、新封面恢复。

这是传输保护修改，无新增或调整可见界面；设备文案/布局仍需另行设计后才能变更。真机验收待恢复桥接后记录。

## Windows 对齐

Windows `Tab5Assets.NextChunk` 同样会无限重建未确认资源循环；后续需同步有限轮数、确认等待和后台诊断，并覆盖 Wi-Fi/USB/BLE 共享预算。保留 Windows 现有打乱分块顺序策略。此次尚未修改 Windows 封面实现，不影响既有发送恢复的跨平台修改。

## .298 重启后的反例（不能用先前通过覆盖）

R46 在 .298 安装重启后又出现一份 336×336、44,361 字节 JPEG 三轮未确认（generation=5、USB 已确认 107 个分块、limited=1）。用户看到先到 100% 再停 0%。这说明三轮上限仅止住循环，不能使该图显示成功。之后用户报告恢复时，后台已经是 generation=7、334×336、45,998 字节的新资源，第一轮确认；不能视为同图故障自动消失。

R47 候选增加一次同尺寸兼容路径：JPEG 三轮仍未确认后，对协议允许的宽度不超过 336 的封面，在 Mac 解码为同宽高 RGB565，使用设备已有 rle565 格式，再进行有限重试。来源未变化时不重新走 JPEG，不缩小图像；宽于既有 rle565 上限的图像不会偷偷缩小，仍保留重试限制。转换失败也只尝试一次。此兼容路径尚不能确定先前 JPEG 未确认的底层原因。

同时新增只含数值/固定错误标签的 USB 与设备运行诊断，用于区分回执拒收、超时及内存情况。无协议改动、无再次刷机。后续以 R47 的实际失败恢复与可见画面为准。

R47 最终本轮复验：用户重新播放之前停在 0% 的歌曲，等待后确认封面正常。后台记录 336×336、44,361 字节 JPEG，第一轮收到确认（R47 pid 56701），没有触发 RGB565 兼容回退。与 R46 失败样本尺寸、字节数相同，但无资源摘要，因此按用户确认记录为故障歌曲复播成功，不凭尺寸/字节数宣称字节完全一致。兼容回退的实际触发仍未实测；历史 JPEG 偶发未确认底层原因仍待进一步证据，不能把通过一次复播写成根因彻底关闭。

R47 正式构建脚本、签名、28,814 项 parity、独立追加回归及音乐采样通过；XCTest 仍缺模块。保持 R47 后台运行，TAB5 .298；未提交、推送或公开发布。
