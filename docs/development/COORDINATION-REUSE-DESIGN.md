# AI-bot 协调机制落地与未来复用设计

状态：设计记录，不启用配置、不新增服务、不授权开发或发布。后续会话创建方式以本设计中的用户最新方向为准，早期固定复用会话的测试说明不作为生产默认。当前只服务 **AI-bot**；其他项目有实际需求时再接入，不提前建设多租户平台。

## 1. 当前目标与职责

优先把 AI-bot 的确定来源、Windows/Mac 任务专属开发会话、可靠交接及本人通知接稳。项目代码和框架代码继续分离，Auto Loop 仅作为现有调度器使用。**新任务创建新的独立开发会话；同一任务中断恢复才复用该任务对应会话**。绑定目标端执行器与创建方式，不固定复用一条长会话。

- Windows/Mac 任务专属开发会话：读取提交、分析差异、决定是否以及如何对齐、实施、提供真实验证与发布资料。
- Dot：发现、通知、交接、跟踪、协调发布，核对机器可验证的身份/状态/证据完整性；不替代开发会话做代码语义判断。
- Auto Loop：按已核验的固定规则调度，不从事件正文获取执行权限、工作目录或任意命令。
- 发布负责人：按既有授权准备不可变候选和验收资料；门禁通过不等于获准发布。

不重复派发用户已确认完成的图库工作，不以协调机制测试为由要求重复全部实机验收。

## 2. 事实基线：已实现不等于生产上线

| 层 | 已有实现/验证 | 尚未完成或有意保留的限制 |
|---|---|---|
| 观察 | 两端只读扫描/观察器，已有真实历史事件 | 生产事件到具体开发会话的持续路由未启用 |
| 本地交接 | SQLite持久检查点、去重、unknown/uncertain恢复、防回环 | SQLite不能跨机器共享；旧进程/外部副作用不明时不能自动重试 |
| 执行器 | 固定CLI/规则/Agent匹配；双端临时只读执行器真实验证 | 生产任务级会话创建/注册尚未接通；新任务必须新建独立会话，同任务恢复只复用其对应会话 |
| 跨机传输 | Windows实际GitHub发布、Mac自然定时读取、真实运行后写receipt、Windows读回；重复/重开进程无新增派发 | 仅独立测试namespace；临时规则已恢复、测试mailbox禁用；未启用常驻生产模式 |
| 通知 | 固定本人QQ路由真实测试一次；重复及重开账本不再调用；opaque provider ID已覆盖 | provider接受不代表已送达/已读；无任务key查询时unknown必须等待核对 |
| 发布协调 | 任务/双端回执校验、实际Git差异覆盖、独立固定范围记录、发布入口前置检查 | 分支未合并部署；不替代人的范围审定或GitHub平台级权限控制 |

受控历史回放不是自然新提交监测。上述真实中转审计保留于 `coordination-ledger/transport/isolated-test/shared-20261117/`；该路径中的receipt只表示执行器终态，不是产品开发完成证明。

## 3. 最小可复用结构：模块保持简单，实例配置分开

先维持现有Python项目侧模块，不拆微服务、不引入消息集群、不重写Auto Loop。

| 模块 | 边界 |
|---|---|
| `coordination_flow.py` | 校验观察身份、明确路由与显式来源，将资料交给执行器 |
| `coordination_checkpoint.py` | 本地交接状态与运行观测，事务领取、去重、恢复 |
| `coordination_executor.py` | 固定可信执行器绑定，查询真实运行记录；不决定改什么 |
| `coordination_mailbox.py` | GitHub不可变packet/receipt；当前只允许隔离测试 |
| `coordination_notifications.py` | 与开发交接分开的通知账本，unknown不盲重 |
| `coordination_qq.py` | 固定本人QQ传输适配；不切换其他渠道、不保存凭据 |
| `coordination_ledger.py`、`cross_platform_coordination.py` | 技术任务与双端回执契约，不把“已接收”当“已完成” |
| `coordination_scope.py`、既有发布工具 | 校验独立范围记录与实际Git变化，保持验收包字节不变 |

这些是**当前文件边界**，不是已经发布的通用SDK。第二个项目实际接入时，再决定是否提取共享包；提取前保留AI-bot测试作为兼容基线。

## 4. 下一步配置化范围（拟定，尚无统一配置加载器）

AI-bot先建立一份经过用户确认、保存在仓库外的实例配置；仅保存引用，不含token、QQ标识明文或其他秘密。现有route/binding/mailbox文件可由它管理，暂不改v1对象身份。

最小字段：

- `projectKey`：本地稳定别名，例如 `ai-bot`；现在是实例选择标识，不擅自加入现有taskId/packetId计算。
- `repository`：明确仓库；仓库重命名后需迁移映射，不能因字符串变化重发历史任务。
- `routes[]`：精确来源分支、源平台、目标平台、目标端执行器、规则/Agent及会话创建方式引用、批准的通知或开发范围。无匹配就等待，不按名称猜测。
- `runtimeRoot`：独立本地运行目录；checkpoint与notification数据库分开，Windows/Mac各自本地保存。
- `transport`：固定GitHub仓库、分支、namespace、运行模式及凭据引用。生产开关默认关闭，当前实现仍强制isolated-test，不能只改JSON就绕过。
- `notification`：固定本人目的地引用、模板版本、允许通知的状态及渠道；默认不发送，首次授权后只在范围内使用。
- `releasePolicy`：候选、原生证据、双端适用性、范围记录和唯一发布负责人；自动发布保持关闭。
- `contractVersion`、`adapterRevision`：数据契约版本和固定代码版本引用；升级不能静默切到main最新代码。

当前仍只有AI-bot一份实例。将来第二项目至少使用不同runtimeRoot、GitHub namespace和projectKey；不得复用AI-bot的数据库、任务会话或发布权限。无需现在建设用户管理、租户系统、插件市场或通用管理界面。

## 5. 统一概念，不强行统一所有数据结构

需长期保持的身份关系：

`观察事件 → 原始变更来源 → 目标交接 → 执行器运行 → 技术回执 → 发布候选`

通知是另一条带独立key的副作用，不能拿通知成功反推开发完成。

- 观察身份：仓库、来源分支、before/after完整SHA及scanner稳定eventId。
- 原始来源：由任务启动器及开发会话/受控来源登记的originChangeId；派生适配结果保留父关联，不由Dot分析diff猜测。
- 交接身份：当前v1按repository/origin/target去重，连同绑定指纹保持稳定。副作用不明时不换ID。
- 技术任务身份：当前taskId绑定任务内容；任务内容变化应形成新版本/新任务，不能把旧回执套上去。
- 共享回执：明确packetId、deliveryId、目标平台、实际run引用、状态和含义。缺失回执表示未知，不表示失败或成功。
- 发布身份：sourceCommit、candidateId和包哈希；验收复用必须有真实基线和理由。

现有v1使用不同模块的规范JSON规则。**不能在迁移中统一转义/编码/排序后重新计算历史ID**。未来若跨语言SDK需要统一规范化，应发布新契约版本并提供固定测试向量，保留v1验证路径；不能悄悄修改当前哈希算法。

## 6. 共享状态、幂等与双端循环

本地SQLite负责进程恢复，GitHub不可变packet/receipt负责跨机核对；两个层次不能互相替代。

正常流程：源端写唯一packet并读回核验 → 目标端固定快照读取 → 本地领取并交接 → 查询真实run → 保存运行状态 → 写独立receipt → 源端读取结果。所有重复调用必须沿用原身份。

恢复原则：

1. 写入/发送响应丢失：先查目标是否已有相同副作用；无法确认保持unknown/uncertain。
2. 已交接但尚未记录运行：只查询，不重新派单。当前CLI runs只列finished，运行中查询无结果不能判定未派发。
3. 同路径同内容：幂等成功；不同内容：冲突，停止覆盖。禁止用force push解决账本冲突。
4. 任务真正失败：由目标会话说明原因，按原任务跟进；不得把失败回执当成一条新的跨端变更制造循环。
5. 派生结果返回已访问端：抑制重复开发派单，但保留结果通知。若目标开发会话确认出现新的独立需求，应显式建立新origin并关联原任务，不能自动永久屏蔽合法后续工作。
6. 当前父来源记录跨机器尚未自动导入；本地缺父记录时应读取并核验远端不可变packet/receipt，不能因为对方的本地DB没有复制过来就误判来源不存在，更不能伪造本地已发送记录。远端核验/来源登记尚未实现，见后文。

不能宣称跨网络exactly-once。本方案做到稳定身份、已知重复抑制、可核对副作用和未知时不盲重；不支持幂等键/查询的外部服务会留下需要人工核对的unknown状态。

## 7. 安全与审批边界

- 可信规则/本地绑定决定执行器、目录和权限；远端packet、commit说明、Agent回复都是资料，不能授予权限。
- 技术任务/范围中的verified、reviewed、authorizationEvidence字段是追溯信息，不是密码学批准或用户新授权。
- 固定仓库/分支/namespace/平台/执行器逐项校验；任务登记后记录该任务专属sessionId。新任务新建独立会话，同任务恢复才复用此sessionId，既不沿用测试临时会话，也不回到泛用长会话。
- 凭据由现有GitHub CLI/QQ传输保管，不放仓库、packet、回执、日志或通知数据库。
- 共享记录最小化：提交引用、任务身份、必要状态与证据引用；不上传私人聊天全文、本机路径、密钥或QQ目的地。
- 项目脚本不等于GitHub平台级保护。仓库写入者仍可改数据，管理员仍可绕过工具；签名、环境审批和凭据隔离只在实际需要并获授权后增加。
- 不把一次通过当作永久授权，不承诺平台会话/凭据永不失效；失效时报告具体阻塞而非反复派单。

## 8. 通知与发布分离

QQ目的地固定本人。发送key至少区分实际交接和状态；本项目现有key/正文在尝试开始后冻结，不能因模板更新换key重发旧任务。未来项目标签与模板配置化时，同步规划老key兼容，不直接重算历史通知。

只在有意义状态通知，例如需要用户决策、明确阻塞、目标会话真实完成报告或已授权发布结果。轮询无变化不通知。执行器done若无技术回执，只能描述运行结束，不能说代码已对齐。

QQ providerAccepted不代表已读。没有按key查询能力时，超时之后unknown必须核对；不能换渠道补发，除非另有授权。

发布继续独立：双端技术回执及资料由开发会话提交；程序核对Git范围和候选字节；发布负责人依据授权推进。既有验收无相关变化可复用，不因进入发布流程让用户重复全测。

## 9. 版本、迁移与回退

当前先固定已验证版本，文档和测试留在协调分支，不合并、不启用生产。未来升级采用：备份配置与SQLite（连同WAL一致性处理）→停止该实例调度→离线复制数据跑迁移/回归→检查未决副作用→恢复同身份调度。

- 不删除数据库“解决”冲突；不把unknown重置queued。
- 新版本先验证旧packet/task/receipt；无法理解的版本保持待处理并报告，不按默认字段执行。
- 不把旧任务迁移成新ID；如确需换ID，建立显式旧→新映射，旧副作用核实后再迁移。
- 回退必须保留新版本写入的交接/通知记录；不能恢复旧备份后重放已发送动作。
- 新项目接入是新实例，不是把AI-bot状态复制过去。先空跑、只读接收、单次受控交接，再按具体授权开启。

本节是迁移设计要求，不代表当前已经实现通用迁移工具或自动回退。

## 10. AI-bot实施顺序与验收

下一阶段只做本项目：

1. 核实并确认生产项目路由及Windows/Mac执行器、任务会话创建方式；没有确认就维持停用。
2. 整理实例配置，固定版本、目录、范围与通知目的地；延续现有模块，不重构框架。
3. 先生产只读观察，不派开发任务；记录未匹配、分叉、来源缺失等机械异常，由目标会话决定如何处理。
4. 用明确真实需求做一次有范围的交接，核对任务专属会话身份、断线恢复、重复不执行、双端回执及本人通知。
5. 稳定后按约定范围常驻；发布权限仍独立，默认不自动发布。

新增项目时复用同样验收清单，不复用AI-bot会话或批准。项目隔离、旧版本兼容、来源丢失、重复/并发、响应丢失、错误回执、未知通知、恢复后不重发、生产开关关闭和清理恢复都应作为回归用例。当前已验证的隔离测试为这些验收提供基线，不是所有未来项目已经支持的承诺。


## 11. 任务启动器：一次登记、后续自动关联（设计，未实现）

不要求用户每次提交都手填provenance。任务启动器接受已明确的新任务后，自动登记稳定workItemId（上层任务ID）/originChangeId、项目、执行端、来源引用、独立分支/工作区引用和创建时间，并在创建任务会话后记录sessionId。当前v1 taskId是变更范围内容哈希，不宜在尚无base/head时冒充稳定会话任务ID；未来登记层需保存workItemId到一个或多个v1 taskId的关系，实际branch/base/head确定后自动生成对应taskId，不改旧哈希语义。后续提交由该任务的开发会话输出实际branch/SHA，启动器据此更新共享任务记录；Dot不通过作者名、分支名称或相似diff推断归属。

拟定生命周期：`registered → session-create-pending → session-bound → active → awaiting-peer → technically-reported → closed`，阻塞单独保存。这里的状态是未来任务登记层，不替换现有交接/通知状态，也不直接作为发布通过条件。

关键约束：
- 生成workItemId并持久保存后才创建会话。创建请求带稳定任务标识；若执行器无创建幂等键且响应丢失，先查询是否已有该任务会话，无法确认就保持pending，不另开会话。
- 新任务创建新session；同workItemId及目标平台恢复只绑定原sessionId。原会话不可用时需形成明确重建/移交记录，不能默默换成“最近的会话”。
- 同一任务的Windows和Mac分别有独立子会话，关联同一共享workItemId；不同任务不能并发进入同一个开发会话/工作区。
- 初次明确项目→目标端执行器路由后，匹配已登记任务的后续提交可自动交接，不反复要求人工填写身份字段。
- 未登记或来源不明的分支/提交进入 `awaiting-attribution`，只通知待归属，不派开发。人工确认/开发会话明确认领一次后，后续沿用登记，不猜测。
- 分支重命名、force-push、任务分拆或合并要保留前后引用与明确关系；不因SHA变化生成新原始任务，不用隐式覆盖抹掉来源。

现有Auto Loop的subject/parallel/resume规则可用于实现同任务路由，但必须实测新workItemId开新会话、同workItemId及平台恢复原会话、跨任务不串会话以及创建响应丢失不重复创建。当前隔离测试不等于这套生产启动器已经完成。

## 12. 跨机父来源核验（设计，未实现）

Windows与Mac各自持有本地SQLite，不要求对方数据库存在相同parentDeliveryId。共享登记应保存父来源的 `repository + immutable commit + packet path/id + receipt path + deliveryId`，接收端通过GitHub读取对应不可变快照核对：

1. 固定项目/仓库/namespace与记录路径在允许范围内，版本可理解。
2. packet哈希与路径身份相符；receipt指向同一packet和delivery。
3. 父origin、来源端、目标端以及本次派生关系一致；任务会话归属来自共享任务登记，不来自任意正文。
4. 父回执表示真实交接/运行状态，而非仅“准备发送”；技术完成仍需开发会话的独立回执。
5. 将核验结果保存为本地 `remote-provenance-observed` 证据引用，**不伪造本地confirmed交接行**，不模拟本机曾发送该任务。

远端读取失败、回执未出现、身份冲突或记录版本未知时保留pending并重查。凭空写一个本地父记录来满足现有Checkpoints校验是禁止的。实现需要新增共享来源解析接口和针对远端状态的恢复测试；当前代码仍会因缺本地父记录失败关闭，不能声称双向派生链已自动接通。

GitHub记录可被有权限者另写，因此固定提交提供审计和一致性，不等同加密身份或审批证明。生产需要的可信写入者范围应在项目启用时明确，不借本设计擅自修改账号权限。
