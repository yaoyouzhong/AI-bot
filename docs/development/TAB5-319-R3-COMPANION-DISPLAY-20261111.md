# TAB5 319-R3 萌宠对齐与总览显示

在 [319-R2](TAB5-319-R2-CLAUDE-HEADPHONES-20261111.md) 之上应用[源码补丁](TAB5-319-R3-COMPANION-DISPLAY-20261111.patch)，继续使用已授权的原版耳机帧。应用和协议版本为 `0.2.319-ui`，内部修订为 `R3`。

## 视觉目标

以 1280×720 横屏的可见轮廓为基准。总览萌宠位于任务卡右侧，工作状态的目标高度约 120 像素、中心约 (658,244)。屏保的目标高度约 300 像素、中心约 (632,329)。两种造型各自保持原比例，原帧之间的横向位移继续可见。Claude 普通空闲与离线动作也适当放大，等待、完成与探索动画沿用各自的道具比例和位移。继续使用 R2 的字体、文字颜色、卡片间距、按钮及触控区域。

## 显示诊断与修改

R2 真机在总览左侧复现两次短暂闪动，报告后分别读到累计欠载 9 和 10。R3 构建期间继续读取同一次 R2 启动，13:49:53 至 13:54:56 获得 78 个新鲜样本，连续总览 302.718 秒，亮度 79%。欠载从 14 增至 16，绘制错误和扫描间隙均为 0。计数来自固定 SDK 的 LCD FIFO 欠载中断，表明扫描供数发生过不足。单次采样无法判断具体是哪项并发工作造成了用户看到的那次闪动。 [Espressif LCD 欠载说明](https://docs.espressif.com/projects/esp-faq/en/latest/software-framework/peripherals/lcd.html#esp32-p4-drives-a-mipi-dsi-lcd-with-a-flashing-blue-screen-and-the-message-can-t-fetch-data-from-external-memory-fast-enough-underrun-happens)

显示刷新路径在第一次遇到某种大损伤条带时，除了实际旋转，还会在同一回调里对多种实现反复测速，最多额外进行 16 次像素遍历。修订后每个条带只旋转一次。大条带使用现有的 8 KiB 内部 RAM 工作区分块转置，分配失败或条带较小时走既有正确性已覆盖的 CPU 旋转。总览显示期间，预热和修复其他页面的后台缓存每步最多处理 32 行等量像素，原为 64 行。已发布的缓存仍在完整新快照就绪后才交换。

保留已知可用的面板时序和现有驱动路径。显示欠载中断会记录最后一次欠载的时间、页面、屏保以及当时的刷新、传输、缓存和 Flash 阶段。USB 和 Wi-Fi 现有显示诊断中追加 `lcd,1,<累计次数>,<开机微秒低32位>,<页面>,<屏保>,<阶段位图>`。阶段位图从低位开始每 4 位依次为刷新、传输、后台缓存、Flash。数据用于关联现场现象，刷新或缓存处于某阶段本身不足以认定其为根因。

## 候选构建

固件 BIN 7,052,624 字节，SHA-256 `6b6875a1257b879d1e67a0b2fecc229e88447037a326ea974ff5317951b00962`。运行 ELF SHA-256 `928760af429bd71a2d0e782dcbbffd911b3982e65e5d0aa65de4de6033e90783`。ESP-IDF、图库任务栈预算、绘制后端及生产镜像加载器均已通过。候选与采样证据位于 `artifacts/t5-319-r3/`。

实际 LVGL 渲染显示，工作状态的可见高度在总览为 Claude 120–122 / Codex 120 像素，在屏保为 Claude 294–301 / Codex 299 像素。按六帧移动范围的中心比较，两处与 Codex 都相差约 2 像素以内。两者保持各自轮廓宽度，图片、状态文字和按钮之间留白正常。详见 `working-comparison.png`、`working-dimensions.json`。

旋转回归覆盖 378 种像素布局。Claude 384 帧解码、边界和工作动画时序，Codex 九种状态，25 帧滑动像素对照，缓存完整发布和中途更新，Claude 屏保左侧 96 帧离屏检查，以及实际 sidecar 更新说明预览均通过。完整 LVGL 十二页回归通过。R3 已由准备脚本写入本机固件交付路径，R2 原包保留。

## 真机验收

14:01 经 Wi-Fi 完成压缩传输 5,121,345 / 5,121,345 字节，设备重启后恢复 USB 和 Wi-Fi。14:02:09 读回 R3 精确 ELF，启动分区 `ota_0 / VALID`，写入 7,052,624 / 7,052,624 字节，升级错误 0。

开机约 6.10 秒在总览录得一次欠载。新诊断报告后台缓存正在处理、界面刷新及 Flash 阶段为空闲。该点支持继续关注缓存占用，未证明缓存是唯一来源。

设备先进入屏保预览再返回总览。14:03:05 至 14:10:05，在总览 79% 亮度下获得 141 份新鲜样本、419.328 秒。累计欠载始终为 1，绘制错误和扫描间隙为 0，背光写入没有增加。用户确认约 6 分钟的实屏观察内没有看到左侧闪动。该结果覆盖本次连续观察窗口，开机欠载及其具体触发源仍需保留在记录中。

14:12 用户再次报告屏闪。13:50 的基线和本次观察都在同一面板时序、79% 亮度下进行。14:11:58 的 USB 新鲜样本确认欠载从 1 增至 2，最后一次为开机 615.632 秒，页面 0、屏保关闭、绘制错误与扫描间隙仍为 0。缓存和 Flash 阶段均空闲。传输阶段为提交回调已返回，该阶段不能证明 DMA 在欠载时仍活跃。R3 的总览无闪动验收未通过。原始读数见 `artifacts/t5-319-r3/flicker-report-1.json`。

随后的两次实屏闪动报告后，USB 采样分别确认欠载增至 3 和 4，仍为总览、79% 亮度，绘制错误及扫描间隙为 0。第 3 次欠载与后台缓存处理重叠，第 4 次欠载时缓存空闲，两次 Flash 阶段均为空闲。记录见 `flicker-report-2.json` 和 `flicker-report-3.json`。继续在 LCD 供数环节验证，避免把所有闪动归到缓存。

用户确认实屏高度接近，并指出 Claude 仍比 Codex 宽。R3 以等比例缩放保留两套造型的宽高比。另用实际 LVGL 渲染验证横向比例的调整方案，工作状态宽度在总览为 Claude 138–140 / Codex 138 像素，屏保为 Claude 345–347 / Codex 344 像素，高度与中心保持上述目标。两套萌宠的离屏回归通过。该方案仅生成预览 `width-working-comparison.png`，真机仍运行 R3。
