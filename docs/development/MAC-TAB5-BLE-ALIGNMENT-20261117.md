# macOS 对齐 Windows 与 TAB5 交接（2026-11-17）

接收分支为 `codex/tab5-calendar-and-claude-idle-20261116`，审阅起点 `1e0b91b`。Windows 候选包、固件和既有实测见[原交接](MAC-TAB5-BLE-HANDOFF-20261117.md)。本轮只修改 Mac 桥接和验证记录，沿用当前设备固件和配对。

| 项目 | Mac 处理与验收边界 |
| --- | --- |
| BLE 状态帧 | 状态/资源逐片等 ATT 回执，只以认证的匹配序号推进完整状态的 delta 基线。局部超时或认证序号迟迟未匹配时，最多恢复两次；清掉基线，状态特征静默至少 5.1 秒，其间允许两个邮箱继续调度。超时写的回调迟到时，从该回调重新算静默。 |
| BLE 首次读 | 已认证连接上的邮箱首读 3 秒到期后释放当前调度，原邮箱等待迟到回调，其他特征仍可用；同邮箱最多允许两次连续恢复。CoreBluetooth 未提供逐次读取消或回调编号，因此在旧回调归来前不重发同特征读。原操作发出 12 秒还未收到回调时，等已开始的业务结束再重连。拿到请求头之后的通知窗口、认证失败与真实断线保持原失败路径。 |
| BLE RPC 重放 | 沿用 `rpcReplay` 能力协商与 `0x0e` 条件。只重放同一窗口的原有密文并逐片确认；在确认边界允许独立语音邮箱工作，返回时从原游标继续，不重复执行业务。暂停的 RPC 仍受原截止时间约束。 |
| 状态快照、图库 | Mac 已独立采集基础快照，Wi-Fi 另有后台成帧缓存；USB/BLE 仍在各自发送路径用快照组装含当下控制字段的帧。Windows 的完整后台成帧和 R3–R5 开发资料不在交接提交里，不能据此宣称等价。设备侧原链路重试由共用固件提供；慢采集、HTTP 响应头前重试和邮箱并行仍需设备证据。 |
| Claude 空闲 | `759a5f7` 已有 Mac 原生识别和日志兜底，无需重复移植。需验证真实终端空闲、工作、待输入、退出和多终端混合。 |
| 日历与总览 | 共用固件提供日历应用入口与 R6 萌宠单行。Mac 无需修改协议，真机需核对应用和总览两个入口、返回路径及数据。 |
| 解锁与 Codex 定位 | Windows WTS、登录助手和 Explorer 路径不适用；保持 Mac 原生授权和 `NSWorkspace`/辅助功能路径。实体按钮、目标会话和 Mac 系统解锁须单独验证。 |

CoreBluetooth 的[读值／通知回调](https://developer.apple.com/documentation/corebluetooth/cbperipheraldelegate/peripheral(_:didupdatevaluefor:error:)-1xyna)使用同一委托方法；[写回执](https://developer.apple.com/documentation/corebluetooth/cbperipheral/writevalue(_:for:type:))仅适用于有应答写。授权的通知窗口与首次读不重叠，超时后不复用对应特征，断开后等待系统断开回调再开始新一代认证。协议、认证、线速和传输优先顺序保持不变。

真机记录按实际桥接来源、可执行文件 SHA-256、固件 ELF 和实际通道登记。USB 管理口可以读取版本、启动槽及发起 RAM 测试；BLE 数据须由设备报告为 BLE。已有探针达到样本后会主动取消，取消后的未完成行不计作传输通过。

## macOS 构建与真机结果

- 本地候选构建自 `2903ee75229e71914137d12677820b87f45e5d3f`，Apple Silicon、Xcode 27.2。Release 构建及 App 严格签名校验通过，可执行文件 SHA-256 为 `9a3d7e3bfc05c0df8f45246a32720e59a30793d5c8783a1148e40b67334ff63d`。原生日常版为 0.6.23；候选从临时目录启动，未覆盖安装。
- `swift test`：538 项，4 项独立夹具默认跳过，0 失败；29,175 项内置隔离检查通过。新增测试覆盖状态失去确认、空邮箱超时、迟到回调、重放让出边界和诊断恢复。用实际 Claude Code 2.1.325 在本机伪终端运行两组隔离回归：连接本地模拟模型，在 Apple Terminal / iTerm 的终端环境参数下都观察到空闲 → 工作 → 空闲；同时验证草稿拦截、文本和图片、追发与中断。旧日志与失去活终端证据由 XCTest 覆盖。多个真实终端混合和系统待输入未实测。
- 实体 TAB5 测试前后读回 `0.2.322-ui`、`ota_1`、`VALID`（状态 2、调用结果 0），运行 ELF `a353981dbe063adff0de128fe41ccf8bd8473df3e97ddd830496b0b1bd6356b0` 与 Windows R6 一致。沿用现有配对和镜像。
- **USB**：同一候选，完成 3 次上行、2 次下行，每次 256 KiB，设备校验错误均为 0。探针主动取消时，第 3 次下行只收到 48 KiB，不计入通过。已安装的 0.6.23 基线也完成相同数量的双向样本。

- **Wi-Fi 与日历**：用日常 0.6.23 与同一台 R6，设备完成经认证的 Wi-Fi 临时切换、读回和 USB 恢复；前后展示设置相同，未改持久连接方式。通过 USB 在真机点击「应用 → 日历」和总览日期，两个入口都打开月历并各自返回原页；日期、农历、节气与“近期生日：无”可见。未专门造生日或节假日数据。总览萌宠旁状态在同一行。

## 补齐遗漏：Codex 桌面快照

R6 总览在已安装基线和 Mac 候选都把正在处理的会话标为「状态未知」。本机只读探针确认：实际桌面拥有者对同一个会话返回的快照是版本 13，运行态 active、当前轮次 inProgress；Mac 只收版本 11，因此有任务目录，但显示不了实时活动。Windows `759a5f7` 已让 `ReadActivityAsync` 不限快照版本，这项原交接没有写入；该提交仍对完整读取和控制使用 11。

两端现在都按已认证的拥有者、准确会话及已知字段判断快照，活动、历史、送达核验及控制不比较外层快照版本。不能识别任务状态、请求列表或轮次时，按现有规则拒绝或显示未知。发送、中断、分页、已读确认各自发出的操作请求仍使用现有的消息格式和方法版本；遇到对端拒绝不猜测版本、不改发另一份请求。TAB5 协议不变。

另查到 Codex 已读状态文件仍使用桌面明确命名的 `electron-thread-read-state-v1` 存储格式，发出的已读确认等消息也各有版本字段。这些不是对 Codex 客户端发行版或实时快照的绑定。另一个独立领域是 Claude：Mac 的 VS Code 适配仍限制 CLI 2.1.314 / 2.1.318，后台 daemon 的 Mac / Windows 入口分别有 2.1.318 / 2.1.319 限制；未在这次 Codex IPC 修复中改动。

- 修复候选源码 `a6ee531c7692119ecc1673842dacf5a1f8b56f43`；Mac 可执行文件 SHA-256 `50fbacb914eb922e13ec3b98af20a36ea314004f2c5cf6cd4892d4545ca9d08b`。Mac 539 项测试（4 跳过、0 失败）、Release、签名校验通过；Windows Release 跨平台编译 0 警告、0 错误，原生 `--status-once` 和自测仍需 Windows 环境。
- 用 Mac 生产 IPC 读取代码直连本机实际 Codex 拥有者，同一任务读取结果为 `working`。随后使用同一签名候选，通过 USB 自动取回 R6 的 1280 × 720 真机总览，原先显示「状态未知」的任务显示「工作中」和工作动画。自动验收确认展示设置前后相同，一次多余的总览点击未获回执；最终画面由设备实际回传。没有发送消息或中断真实任务。
- 「仅蓝牙」时设备接受 USB 管理状态，但 USB 自动验收在读取展示设置阶段未获回执。用户恢复「自动选择」后，从真机 USB 镜像重新核对该设置；候选之后仍运行，日常安装包未覆盖。证据见本机 `artifacts/mac-tab5-ble-alignment-20261117/codex-device-verification/`。
